Built on Stellar, Soroban, USDC (Stellar Asset Contract), OpenZeppelin stellar-accounts, x402 and Rust. These are technologies Kovan uses, not partners.

§01 The problem

AI agents now pay for their own data, one API call at a time. To let them, you either hand over a wallet they can empty, or refill it by hand forever. A bug, a loop or one injected prompt is all it takes. Kovan gives every agent a budget, not a blank check.

Who it's forDevelopers and teams running agents that buy data, RPC or API calls per request.
What changesThe rules live on-chain, in the agent's own wallet. Not in a prompt, not in a server.
What stays yoursNon-custodial. Funds sit in contracts you control; freeze or pull them back anytime.
§02 How it works

Three moves.
One of them is a no.

Four Soroban contracts: a pool, a per-agent OpenZeppelin smart account, a covenant policy and a signature verifier. The owner sets the rules once; every payment is checked against them by the network.

kovan / architecture01 · configure
01 / OWNER CONFIGURES

Lock USDC once. Write each agent's covenant.

The owner funds one kovan-pool and calls create_agent. The pool deploys a fresh OpenZeppelin smart account for that agent, frozen at creation with the covenant as its only rule.

  • Draw limit carved from the pool, never more than what's locked
  • Allowed payees, with a per-transfer cap and a total cap
  • Allowed contract calls and an expiry ledger
02 / AGENT SPENDS

The agent draws and pays, per call.

The agent pulls up to its draw limit into its own wallet and pays an allowlisted provider over x402. Every outgoing transfer is authorized by the wallet, and the wallet asks the covenant policy first.

  • draw moves only the agent's share out of the pool
  • Per-call USDC payments to providers on the list
  • return_funds sends unspent USDC back to the pool
03 / NETWORK REJECTS

Anything outside the covenant simply fails.

A new address, an amount over the cap, an expired covenant, a revoked agent: the policy refuses to authorize and the transaction fails on Stellar. No server to trust, no prompt to obey.

  • The agent can't call admin functions on its own wallet
  • The owner can revoke any agent at any time
  • Revoking a parent freezes its children
§03 Why Kovan

More than a spending limit.

Plenty of agent wallets have a cap. Kovan adds what a cap alone can't do: one pool for many agents that can't be over-assigned, delegation that can only narrow, and refusals you can verify on-chain.

A Shared pool

One pool. Never over-assigned.

§06 Guarantees

Enforced by contracts,
not by good behavior.

Each guarantee is covered by the open-source test suite and enforced by the contracts deployed on Stellar testnet.

G · POOL INVARIANT
Σ draw_limit(agents) ≤ locked(pool)

The pool can't promise money it doesn't hold.

Creating or amending an agent fails if total limits would exceed the locked USDC.

G · DRAW
draw(0.60) → ✕ > 0.50

Draw stays under the limit.

Only the agent's own share ever leaves the pool.

G · PAYEES
to ∈ allowlist ∧ amt ≤ cap

Allowlisted payees only.

Per-transfer cap and total cap, per payee.

G · CALLS
contract.fn ∈ allowed

Allowlisted calls only.

Contract, function and argument caps are checked too.

G · EXPIRY
ledger < expiry

Authority ends on time.

After expiry, spending stops. Returning funds still works.

G · SELF-BOUND
rules = { agent key + covenant policy }
admin rule = ∅

The agent can't rewrite its own rules.

Its wallet has a single rule and no admin rule. The policy rejects calls from the wallet to itself.

G · DELEGATION
child ⊆ parent in every dimension

Children are narrower. Revoke cascades.

A child can't exceed its parent on any limit; revoking the parent freezes the child; closing the child returns its limit to the parent.

G · RECOVERY
return_funds() always works

The owner gets funds back without the agent's key.

At creation, the agent wallet grants the pool a USDC allowance, so unspent funds can be pulled back after a revoke or expiry.

§08 FAQ

Straight answers.

Isn't this just a spending limit?
A spending limit caps one wallet. Kovan adds a shared pool that can never assign more than it holds, parent-to-child delegation where a child can only be narrower, and owner recovery without the agent's key. The per-payment rules are one part of a covenant.
What stops the agent from changing its own rules?
Its smart account has exactly one rule: the agent's key plus the covenant policy. There's no admin rule, and the policy rejects calls from the wallet to itself. Only the owner can amend limits, through the pool.
Who holds the money?
Kovan is non-custodial. USDC sits in the pool contract and in each agent's own smart account, never with us. The owner can revoke an agent and pull unspent funds back with return_funds.
How does x402 fit in?
Providers charge per call over x402. The payment is a USDC transfer from the agent's smart account, so the covenant checks it like any other transfer. Settlement from a contract account follows the x402 Stellar spec and facilitator code, and we're validating it end to end on testnet.
Is it live? Is it audited?
Kovan is in public beta on Stellar testnet, where USDC has no value. It hasn't been audited yet; a security audit comes before any mainnet launch.
What's next?
Agent reputation, multiple pools per owner, and mainnet, with a security audit before any mainnet launch. The owner dashboard and the agent runtime are already part of today's MVP. See the roadmap in the repo.
