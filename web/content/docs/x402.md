# Paying with x402

[x402](https://x402.org) lets an API charge per request: the server answers `402 Payment Required` with its terms, the client pays, and a facilitator settles the payment on-chain. On Stellar, the payment is a single USDC `transfer(from, to, amount)`.

## Why a Kovan agent can pay

The covenant judges the **transfer**, not the rail. An x402 payment from an agent's wallet is a USDC transfer like any other: it passes only if the payee is on the agent's providers list and the amount fits its caps, before expiry. A prompt-injected agent pointed at an unknown "paid API" can't pay it.

## Paying from a smart account

The standard `@x402/stellar` client signs only for classic `G…` accounts. Kovan's agents pay from a smart account (`C…`), so the payment is built differently:

1. Request the resource and read the `402` terms: price, USDC asset, `payTo` (a `G…` account with a USDC trustline).
2. Build `USDC.transfer(agentWallet, payTo, amount)` and simulate it to get the wallet's authorization entry.
3. Legacy accounts sign an OpenZeppelin `AuthPayload`. New accounts require an owner-approved mandate and a versioned envelope binding the mandate ID, payment ID, purchase-reference hash and expiry into the signed digest. Both use an authorization expiration within the facilitator's limit.
4. Send `{ transaction }` as the x402 payment payload. The facilitator verifies and settles it; on testnet, [x402.org](https://x402.org) sponsors the fees.
5. During settlement, Stellar asks the wallet to authorize the transfer, and the wallet asks the covenant. Allowed: the API returns the resource. Refused: nothing moves.

On testnet, a **legacy account** paid Stellar's x402 demo endpoint 0.01 USDC this way ([transaction](https://stellar.expert/explorer/testnet/tx/781a5f2b560df66d3d6c587ef4f2a283e82421ce16b54565a9a64a8ba662775d)). A payment to an address outside the covenant was refused by the wallet with `#3904 PayeeNotAllowed`, before anything was submitted. This historical transaction does not validate the new mandate envelope through the live facilitator.

## Status

x402 HTTP handling is implemented in the Kovan console (`dashboard/lib/agent-x402.ts`), using `@kovan-protocol/sdk` for contract authorization. The SDK and CLI do not independently fetch paid resources. The console discovers and reviews a quote first, then requires the same `quoteId` and a persisted `requestId` when paying. New accounts also require `mandateId`; the signed reference is the quote hash, and `paymentIdForRequest(requestId)` supplies replay protection. Exact grants bind the quoted recipient/amount/reference; budget grants limit multiple purchases. Unknown settlement outcomes must be reconciled before another purchase.

The new contracts have passed a live **direct-payment** mandate lifecycle with disposable testnet XLM. Live x402 facilitator acceptance for this release remains unverified. The chain enforces hashes and spending rules, not URL contents, work quality or refunds. This is native Kovan authorization, not AP2 credential conformance.
