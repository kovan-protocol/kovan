# Kovan: pool, agents and covenants

Design for the on-chain core of Kovan, built at HackMeridian 2026 (Lisbon, Sun Oct 25 11:30 → Mon Oct 26 12:00 WET). Stellar **testnet only**. Track: Stellar Composed, "Agents that spend".

Background and event rules live in the parent planning folder (`../hackmeridian/docs/`). This document supersedes the "Action Bonds" naming there: the project is **Kovan**, the contracts are **covenants**.

## Intent

An owner locks funds in a pool and wants agents to spend from it without being able to drain it. Today the choices are a funded wallet the agent can empty, or a human refilling by hand. Kovan puts the owner's rules on-chain, where the agent cannot change them.

Three layers:

- **Pool**: a vault holding the owner's locked USDC. It enforces one thing: how much each agent may draw. It has no opinion on spending.
- **Agent**: an OpenZeppelin smart account (C-address) holding that agent's own funds, drawn from the pool. The agent runtime signs for it.
- **Covenant**: the rules attached to one agent. It says how much the agent may draw from the pool, and what the agent's wallet may do with what it holds.

Principle, in the owner's words: *the pool is the bank; each agent's wallet is its own funds; the covenant says how much it may take and what it may do.*

Enforcement principle: **the covenant does not trust the rail, it trusts the allowlist.** An x402 payment and a direct USDC transfer look identical on-chain (`USDC.transfer(from=wallet, to, amount)`); the covenant judges them by payee and amount, never by how they arrived.

## Goals

1. The sum of all agents' draw limits never exceeds the pool's locked funds.
2. An agent's wallet can only make transfers and contract calls its covenant allows, enforced on-chain by a policy on the smart account.
3. The owner can freeze any agent at any time; funds can always flow back to the pool.
4. An agent can delegate a narrower covenant to a child agent, carved out of its own allowance.
5. Every rule above has a test that fails when the rule is violated.

## Non-goals

- Spending enforcement by anything off-chain. If the policy can't check it, it isn't a rule.
- Distinguishing x402 from direct transfers on-chain (see principle above; dashboard labels are fine).
- A dispute court. `dispute` records an objection; the owner rules.
- Reputation (stellar-8004), repay ladders, liquidation waterfalls, trading, MPP, mainnet. All roadmap.

## Anti-goals

- Any path where more than the agent's draw limit leaves the pool for that agent.
- Any wallet action the covenant did not explicitly allow succeeding.
- Keys or wallets generated by AI. Humans make every key with official Stellar tooling.
- Inference/LLM costs paid from pool funds (team rule, "Cavos lesson").

## The covenant

One struct per agent, stored in the pool contract and read by the wallet's policy.

### `draw`

- `draw_limit`: max USDC that may move from the pool to this agent's wallet, cumulative over the covenant's life.
- `drawn`: running total.
- Pool invariant: `Σ draw_limit over active covenants ≤ locked`. `return_funds` reduces `drawn`, so returned money can be drawn again.
- Checked by the **pool** on `draw()`.

### `spend`

Rules the **wallet policy** enforces on outgoing USDC transfers. Two allowlists, each with its own caps:

| List | Meaning | Caps |
|---|---|---|
| `providers` | Addresses paid per call: x402 resource servers, or any direct payment to the same address | `per_transfer_cap`, `total_cap` |
| `recipients` | Plain transfers: another agent's wallet, a treasury | `per_transfer_cap`, `total_cap` |

A transfer passes iff: asset is USDC SAC, `0 < amount ≤ per_transfer_cap`, running total of that list + amount ≤ `total_cap`, `to` is on that list, current ledger < `expiry`, and the covenant is not revoked.

The policy checks `0 < amount` itself regardless of what the library does (known OZ negative-amount concern; VERIFY).

### `calls`

Contract calls the wallet may authorize beyond USDC transfers. A list of `(contract_id, function_name, optional amount cap on a named argument index)`. Empty by default. Same expiry and revocation checks.

### `expiry`

A ledger sequence. After it, `spend` and `calls` refuse everything. `return_funds` still works.

### `lifecycle`

Functions on the covenant, callable as marked.

| Function | Caller | Effect |
|---|---|---|
| `return_funds(amount)` | agent, or owner | Moves USDC from the agent wallet back to the pool. Always allowed, including after expiry or revocation. Decrements `drawn`. The wallet policy allows transfers to the pool address unconditionally. |
| `settle()` | agent | Marks the covenant as settlement-requested. Owner confirms with `close()`; closing requires `drawn == 0`. |
| `dispute(evidence_hash)` | agent or owner | Records a hash and the disputing party. The owner resolves with `resolve_dispute(outcome)`. No funds move automatically. |
| `delegate(child_params)` | agent | Creates a child covenant and child wallet. Child `draw_limit ≤` parent's remaining (`draw_limit − drawn`), and is deducted from the parent's `draw_limit`. Child `spend`/`calls` lists must be subsets of the parent's, with caps ≤ the parent's. Child expiry ≤ parent expiry. Revoking the parent revokes all children. |

### Owner powers (on the pool)

| Function | Effect |
|---|---|
| `fund(amount)` | Locks USDC in the pool. |
| `create_agent(covenant_params)` | Creates the agent wallet with the policy, stores the covenant. Fails if the draw invariant would break. |
| `amend(agent, new_params)` | Changes limits. Fails if it would break the draw invariant or cut `draw_limit` below `drawn`. |
| `revoke(agent)` | Freezes `spend` and `calls`. `return_funds` remains. Recursive to children. |
| `close(agent)` | Final; requires `drawn == 0`. Frees the agent's `draw_limit` from the invariant sum. |
| `withdraw(amount)` | Owner takes unlocked funds: `locked − Σ draw_limit`. |

All owner functions `require_auth(owner)`. All agent functions `require_auth(agent wallet)`.

## Invariants (each gets a failing test)

1. `Σ draw_limit (active) ≤ locked`.
2. `drawn ≤ draw_limit` per agent.
3. Transfer refused when: wrong asset · payee on no list · amount 0 · negative amount · amount > per-transfer cap · list total exceeded · after expiry · revoked.
4. Contract call refused when: (contract, fn) not listed · capped argument exceeded · after expiry · revoked.
5. Non-owner calling an owner function fails; non-agent calling an agent function fails.
6. Revoked agent cannot `draw`, and neither can its children.
7. Child covenant cannot exceed its parent on any dimension.
8. `return_funds` succeeds after expiry and after revocation.

## Calls made after the builder review (Claude's; flag any you disagree with)

- **Wallet admin: there is none.** The wallet gets exactly one context rule, `Default`, with one `External` signer (OZ ed25519 verifier + the agent's human-made public key) and one policy: the covenant policy. Because no rule covers the wallet's own management functions, the rule set is permanently frozen (OZ documents this as a caveat; for a covenant it is the point). The covenant policy rejects any context whose `contract` is the wallet itself, so the agent cannot reach `add_context_rule` through the `Default` rule either. Owner-side `return_funds` and `revoke` work without a signer: the wallet's constructor calls `USDC.approve(from = wallet, spender = pool, amount = max, live_until = far)`, which is auto-authorized because the wallet is the direct invoker; the pool then uses `transfer_from(spender = pool, from = wallet, to = pool, amount)`. This replaces the earlier "pool as delegated admin signer" idea, which needs a nested auth entry that simulation does not return.
- **One policy, one rule.** The covenant policy's `enforce` receives `Context::Contract { contract, fn_name, args }` and branches on `contract`: USDC SAC → `spend` rules (`fn_name == transfer`, `args[1]` payee, `args[2]` amount, `0 < amount`, caps, expiry, not revoked); the pool → allow `draw`, `return_funds`, `settle`, `dispute`, `delegate` only; the wallet itself → reject; anything else → `calls` allowlist. Policy state lives in the policy contract keyed by `(smart_account, context_rule_id)`, mirroring OZ's spending-limit policy; the pool is the policy's admin for `revoke` and `amend`. Non-transfer USDC functions (`approve`, `transfer_from`, `burn`) are rejected so the allowance path cannot be forged by the agent.
- **Child governance.** A parent agent may `revoke` and `close` its own children; the owner may too. A closed child's `draw_limit` returns to the parent's `draw_limit`, never straight to the pool. Children carry a `parent` pointer; revocation walks down.
- **`amend` scope.** Numeric limits only (`draw_limit`, caps, `expiry`). Allowlists and `calls` are fixed at creation; to change them, close and recreate. Keeps the policy free of a sync path.
- **Child in the demo.** Contract-level: delegation is shown by a test, a testnet tx and a dashboard row. The child wallet gets a human-made key, but no second runtime spends live on stage unless time allows.
- **x402 settlement shape: verified.** The spec mandates a single `invokeHostFunction` calling `transfer(from, to, amount)` on the asset contract, with no sub-invocations. The policy only needs the `transfer` branch.
- **Cut order if Sun 16:00 slips:** drop `dispute` → `calls` → `settle/close` → `amend`. `delegate` is kept. (Default taken; owner may override.)
